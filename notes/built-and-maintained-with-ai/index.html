Built and maintained with AI.

I direct, an AI agent builds, and a design system that keeps itself holds it all together. Notes on how this site is made.

August 2026

The idea

This site is built and maintained with AI. I decide what it should be; an AI agent builds it. What makes that work is not the AI. It is the system around it: all the design rules sit in one file, the documentation reads that file live so it is always current, and a check stops any page that breaks a rule. The agent reads all of it before it builds. Nobody has to keep the site consistent by memory; the site does it itself.

Most design systems are kept in order by people. Someone updates the documentation every time the product changes, and the day someone forgets, the two start drifting apart: the documentation says one thing, the product does another, and the team stops trusting the documentation. Here that cannot happen, because nothing is written down twice. Everything is written once, in the place everything else reads from. The rest of this note shows what that means.

The architecture

One stylesheet is the truth. Every colour and every space on the site is a token in it, and the reasoning sits next to the values as comments: not what a rule does, but why it is allowed to exist.

The system page documents the stylesheet, but it does not quote it. It reads it: the palette, the metrics and the motion tables are filled at load from the live values, so when a token changes, the documentation changes in the same second. It cannot go stale, because it stores nothing.

A checker holds the law. One script walks every page and fails the build if a colour or a space appears outside the tokens, if a colour misses one of the two schemes, or if a page breaks one of the writing rules. What the stylesheet permits, the checker enforces.

And the agent reads all three before it draws. Every page here was built by an AI agent working in this repository under my direction: it reads the stylesheet's reasoning, the system page's rules and the checker's verdicts, and what it builds lands back in the stylesheet, where the next round starts from.

What it is built out of

The setup only matters because of what it holds. These are the principles the site is built out of: every page is an arrangement of them and nothing else. They are written as decisions rather than moods, often as a plain no, and that is what makes them checkable. What a machine can check, a machine can keep:

One size of type One text size and one display size. Hierarchy is carried by weight and grey, never by scale.
Eight steps of space Every distance on the site is one of eight, 5 to 80 pixels. A special case does not get a ninth.
Hairlines and space Structure is a rule and some room. Zero corner radius, zero shadows, nothing floats on a card.
One palette, two schemes Light and dark are the same tokens wearing different values, so no page has to know which it is in.
One canvas for the work Screens stand on a single shared grey, and a screen leaving an image's edge leaves at a plate's edge.
Motion that answers to rules The page never moves. What arrives on first sight is the ink and the lines, behind the reader's motion preference.
Hover is a pointer idea A hover state exists only where a pointer does, so a touch screen never meets half of one.
Claims from my mouth only The site states nothing about the work I have not said myself. A missing fact gets a visible slot, not a guess.

Where a rule comes from

Not every principle is designed up front. Some get caught. The plate rule above started on a phone: the Donkey Republic case had screens cropped by their images' edges, standing in fields of slightly mismatched grey, and it read as broken rather than intended. The first idea was to mark every cut with a line where the screen goes under. What shipped instead was an arrangement: the plates dropped their padding so the greys fuse into one surface, and the images took places where every cut lands on a plate's edge, where running off reads as deliberate.

Then the decision was written down, in the stylesheet, at the spot where it is enforced. That is the working relationship in one story: I bring the taste call, the agent brings the build, and the rule outlives the conversation because it lives where the machine reads.

The repository keeps the same voice all the way down. The log reads as the site's own logbook; every commit says what the site did, not what a developer did:

The work opens: one page per case The wall replaced the drawers, and every case got an address of its own.
The clips fuse, and the measurement retires iOS renders video colour its own way, so instead of measuring the grey, the plates fused and the clips' own grey became the ground.
The rubber band comes back A scroll fix took away the bounce a phone needs to feel like a phone. The commit that returns it says why.
The face becomes Switzer The whole face swap in one commit, so one command can take it back.

Building with it

Extending the site is now mostly asking. The agent already knows the bands, the tokens and the principles; the checker referees every change; and anything new that earns a rule gets the rule written where the next build will read it.

This is the same architecture as the prototyping harness at e-conomic: a design system on GitHub, explained to a model before it draws, so that what gets built wears the product's own clothes from the first pass. That work is the subject of the first note. This site is where I keep the discipline in practice.

In short

A design system does not have to be kept; it can keep itself. Give the principles one home the product actually reads from, let the documentation read instead of describe, put a check behind the rules, and let the builder read before it draws. What is left for the designer is the part that was always the job: deciding what the principles are.
